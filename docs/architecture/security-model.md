# Security model

## Trust assumptions

| Trusted entity | How trust is established in the demo | Production expectation |
|---|---|---|
| Buyer and seller organizations | Demo enrollment: created by the hackathon's controlled onboarding. Shown as "enrolled", never as legally verified | KYB, domain control, independently verified admin authority |
| Organization signing keys | Generated by ProxyProof and held server-side (`principal_keys`). Used only when an authenticated person approves | Each organization holds its own key in its own KMS or HSM |
| Agent identity | API agents: their own Ed25519 key. MCP agents: a ProxyProof-issued connection token plus a ProxyProof-held key. Test agents: labelled | Agent-held keys, or attested platform identity where a platform offers one |
| Credential issuers | Only the organization's registered key can issue its delegations | Issuer registry and federation |
| Verification engine and executor | ProxyProof server code. Deterministic, with no model involved | Same, with audits |
| Payment confirmation | Authenticated PayPal API lookup, or a verified PayPal webhook | Same |

**A signature proves control of a key and the integrity of the signed data.** It does not prove the real-world identity of a business. That depends on how the key is bound to the business.

## Controls

**Cryptography:** Ed25519 (EdDSA) JWS, using `jose` and Node `crypto`.

**Identity and keys**
- An explicit registry of organizations and agents.
- `cnf.jwk` binding of each credential to one agent key (RFC 7800).
- Proof of possession on every request: the agent signs over a single-use server challenge.
- Organization key status (`key_status`): a revoked key fails every chain it signed.

**Authority**
- Least privilege per action: `purchase`, `research`, `quote`, `issue_invoice`, `request_payment`.
- Limits on amount, currency, category, counterparty and destination, read from the **signed** mandate.
- Delegation expiry. Revocation takes effect at the next check and cascades to child delegations. The status service fails closed (HOLD, never pass).

**Transactions**
- Canonical terms hash. Both agents must sign the same hash.
- Short-lived, single-use execution permits, claimed atomically. The executor re-checks authority immediately before the side effect.
- One live payment attempt per transaction, plus PayPal idempotency keys.

**Records**
- Signed decision receipts, and a signed evidence bundle checkable against `/.well-known/jwks.json`.
- A hash-chained audit log per workspace. This detects edits; it is not legal non-repudiation.

**Isolation and secrets**
- Tenant scoping: every query is scoped by workspace, and the API checks workspace ownership.
- Secrets stay server-side. PayPal credentials are read only in `executor/paypal.ts`. Connection tokens are stored only as SHA-256 hashes.

**HTTP hardening**
- Dashboard: a session cookie plus a custom header (CSRF).
- MCP: Origin validation and bearer-token authentication.
- Strict Content Security Policy, and rate limits.

## Honest limits

- **Demo custody:** one person acts for every organization in the demo.
- **Weaker MCP assurance:** an MCP connection token is a bearer secret. Anyone holding it can act as that agent within its delegation. This is recorded as the connection's assurance level.
- **No platform identity:** platforms do not expose a cryptographic agent-instance identity to MCP servers. ProxyProof does not invent one.
- **No conformance claims:** no AP2, VC, VI, AuthZEN, AAP or MCP-authorization conformance is claimed. MCP OAuth 2.1 (Protected Resource Metadata) is future work.
- **Damage limitation, not prevention:** a compromised agent with a valid delegation can still act within that delegation. ProxyProof bounds the damage; it cannot prevent misuse within scope.
